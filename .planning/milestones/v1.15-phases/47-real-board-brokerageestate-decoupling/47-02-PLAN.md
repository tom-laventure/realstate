## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| background queue → MLS/RETS provider | `SyncListingPhotosJob` authenticates to the board with the resolved brokerage's stored RETS credential |
| shared board data → per-brokerage attribution | the resolved `brokerage_id` decides whose credential is used to fetch board photos |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-47-04 | Spoofing / Repudiation | `real_board_brokerage_ids` picking a brokerage that no longer holds board access | mitigate | The query filters `status: :active` **and** `.without_deleted` (`deleted_at IS NULL`) — the exact pair of conditions `Estate.accessible_by`'s real-board branch requires. A revoked credential is soft-deleted by `BoardCredentialsController#destroy` (`acts_as_paranoid`) and a de-authorized one moves to `invalid`/`suspended`; both are excluded, so a stale or revoked credential can never be selected. Resolution runs per batch at job execution time, not from a cached mapping, so revocation takes effect on the next run. |
| T-47-05 | Information Disclosure | Attributing a shared board listing to a brokerage that is not "the" original connector (D-04) | accept | Photos are board-level data, identical regardless of which active credential fetches them, and the receiving `SyncListingPhotosJob` uses `brokerage_id` solely to select RETS auth material owned by that same brokerage. No per-brokerage data crosses tenants: the selected brokerage already holds active access to that board. |
| T-47-06 | Denial of Service | New resolution step adding per-estate queries to a 500-row batch loop | mitigate | The method is constrained to exactly two set-based queries per batch (estates→board ids, board ids→brokerage id); `find_each` is explicitly forbidden by the acceptance criteria. `MAX_BATCHES`/`BATCH_SIZE` caps are unchanged. |
| T-47-07 | Tampering | `unlink_estates!` deleting shared real-board estates | mitigate | Comment-only change here, but the underlying exposure closes as a side effect of ARCH-01: once real-board `BrokerageEstate` rows stop being written, `brokerage.brokerage_estates` cannot iterate a shared board listing, so a self-deleting brokerage can no longer hard-delete another brokerage's future access to it. Acceptance criteria assert zero executable-line changes so this plan cannot alter the cascade's behavior. |
| T-47-SC | Tampering | npm/pip/cargo installs | n/a | No package installs in this plan — no `Gemfile` change. Package Legitimacy Gate does not apply. |
</threat_model>
