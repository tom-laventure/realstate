# Requirements Archive — v1.6 Domain Management v2

**Archived:** 2026-05-31
**Milestone:** v1.6 — Domain Management v2
**Status:** ✅ All requirements delivered

---

## DUIV — Domain List UI

- [x] **DUIV-01**: Domain list page renders as a vertical list of cards with no column headers; each card displays the domain URL, a plain-language description of what its current status means for the brokerage and its visitors, relevant dates (e.g. decommission date for phasing-out domains), and applicable action controls — Phase 24
- [x] **DUIV-02**: Subdomain card displays a lock icon; hovering the lock shows a tooltip: "This domain is permanent and was assigned at registration." No action controls other than "Set as primary" appear on the subdomain card — Phase 24
- [x] **DUIV-03**: A Primary badge is displayed on whichever domain is currently designated as primary — Phase 24
- [x] **DUIV-04**: Owner-only action controls: add custom domain, delete custom domain, set as primary, trigger manual verification check — Phase 24
- [x] **DUIV-05**: Admin-role users can trigger a manual verification check and view domain status; no mutation controls — Phase 24
- [x] **DUIV-06**: All roles below Admin see the domain list in read-only mode with no action controls — Phase 24

## DADD — Add Custom Domain

- [x] **DADD-01**: Adding a custom domain is a 4-step wizard: (1) Enter domain; (2) DNS instructions — exact CNAME record; (3) Primary preference — shown only when another active domain exists; (4) Confirm — domain appears in list with Pending verification status — Phase 24
- [x] **DADD-02**: Primary preference step (step 3) is shown only when another active domain already exists; if no other active domain exists, the new domain becomes primary automatically upon verification success without prompting — Phase 24
- [x] **DADD-03**: After submission, the domain card appears in the list with a Pending verification status immediately — Phase 24
- [x] **DADD-04**: Unverified (pending) domains that are not verified within 7 days are automatically removed; Owner-role users receive an email warning at day 5 with a direct link to the Domains dashboard — Phase 22

## DVER — DNS Verification

- [x] **DVER-01**: A "Verify now" button is available on any domain in a pending or phasing-out state; pressing it triggers an on-demand verification job — Phase 24
- [x] **DVER-02**: Background verification polling runs every 30 minutes for all pending (unverified) and phasing-out domains as a fallback — Phase 22
- [x] **DVER-03**: Each domain card shows the last-checked timestamp and the current verification state — Phase 24
- [x] **DVER-04**: When verification fails, the domain card displays a plain-language explanation of what was not found (e.g. "CNAME record not detected") — Phase 24
- [x] **DVER-05**: Simultaneous registrations of the same domain by different brokerages are resolved by first-to-verify wins; no deeper conflict resolution is implemented — Phase 22

## DHLT — Domain Health

- [x] **DHLT-01**: Active custom domains are checked every 30 minutes to confirm their CNAME configuration remains valid — Phase 22
- [x] **DHLT-02**: After 3 consecutive failed health checks (~90 minutes of consistent failure), the domain is automatically moved to Phasing out status — Phase 22
- [x] **DHLT-03**: When a domain is auto-moved to Phasing out by health failure, all Owner-role users are notified by email; the email includes: which domain failed, the failure reason in plain language, the decommission date, and a direct link to the Domains dashboard — Phase 22
- [x] **DHLT-04**: If the auto-phased-out domain was the brokerage's primary domain, the health failure email explicitly calls this out, notes that the subdomain is now serving as fallback primary, and prompts the owner to either fix and re-verify or designate a new primary — Phase 22
- [x] **DHLT-05**: Health check cadence (default: 30 minutes) and phase-out duration (default: 30 days) are exposed as named constants in the codebase — not hardcoded inline — so future adjustment requires only a constant change — Phase 22

## DLCX — Domain Lifecycle

- [x] **DLCX-01**: If verification succeeds at any point before a phasing-out domain's decommission date, the domain is fully restored to Active status and the phase-out is cancelled — Phase 22
- [x] **DLCX-02**: The Domains dashboard displays a confirmation message when a previously phasing-out domain has been successfully rescued — Phase 24
- [x] **DLCX-03**: Deleting a custom domain triggers a phase-out period rather than immediate removal; the deletion confirmation dialog shows the decommission date before the user confirms — Phase 24
- [x] **DLCX-04**: If the domain being deleted is the current primary domain, the deletion flow requires the user to designate a new primary before confirming; the subdomain is pre-selected as the suggested replacement — Phase 24

## DPRI — Primary Domain

- [x] **DPRI-01**: Any fully active domain can be set as primary (Owner only) — Phase 22/24
- [x] **DPRI-02**: Domains in Phasing out or Pending verification status cannot be set as primary — Phase 22/24
- [x] **DPRI-03**: All system-generated links (invitation emails, notifications) use the primary domain — Phase 23
- [x] **DPRI-04**: Requests to any non-primary domain are 301-redirected to the equivalent path on the primary domain — Phase 23

## DPRD — Pro Plan Downgrade

- [x] **DPRD-01**: When a brokerage plan downgrades from Pro, all custom domains are frozen — Phase 22
- [x] **DPRD-02**: Frozen custom domains remain live but serve only a redirect to the subdomain rather than the full brokerage site — Phase 23
- [x] **DPRD-03**: The subdomain automatically becomes the primary domain when a brokerage downgrades from Pro — Phase 22
- [x] **DPRD-04**: Frozen domain cards display a Frozen badge with a plain-language explanation and a prompt to re-upgrade — Phase 24
- [x] **DPRD-05**: Owner-role users receive an email notification when the brokerage plan downgrades, explaining the effect on their custom domains — Phase 22
- [x] **DPRD-06**: When a brokerage re-upgrades to Pro, all frozen custom domains are restored to their previous active state — Phase 22

## Future Requirements (v1.7+)

- Multi-domain round-robin / load balancing
- Server-side 301 redirect at the Caddy/proxy layer (current: Rack middleware approach is sufficient)
- Richer conflict resolution for simultaneous domain registrations beyond first-to-verify

## Out of Scope

- Multi-domain round-robin / load balancing — not needed at current scale; separate milestone
- Server-side 301 at the proxy/Caddy layer — Rack middleware approach satisfies DPRI-04; proxy-layer move is a separate infrastructure milestone
- Deeper conflict resolution for simultaneous domain claims — first-to-verify is sufficient; no complex arbitration
- Apple / Microsoft social login — separate auth milestone
- Two-way calendar sync — separate calendar milestone
- Microsoft / Apple CalDAV calendar providers — adapters built; activation deferred to v2
