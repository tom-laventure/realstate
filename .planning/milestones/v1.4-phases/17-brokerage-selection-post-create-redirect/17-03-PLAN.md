## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Wizard state (CreateBrokerageContext) → window.location.href | `state.result.brokerage.id` came from a server response to an authenticated POST; the browser then issues a same-origin redirect (within the application's primary domain controlled by VITE_MAIN_DOMAIN). |
| LoginSuccessful → Redux store | adminBrokerages list returned by `/v1/account/admin_brokerages` (BE-01) — server-authoritative. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-17-08 | T (Tampering) | SuccessStep brokerageId interpolation | mitigate | `brokerageId` is read from `state.result.brokerage.id` — a server response, not a user-controlled form input. The `String()` coercion neutralizes the `string | number` type union without changing trust posture. The `disabled={!brokerageId}` guard prevents action when the value is missing. |
| T-17-09 | I (Information Disclosure) | Redirect URL `https://{MAIN_DOMAIN}/dashboard/{id}` | accept | The brokerage ID is the owner's own brokerage (they just created it); appearing in the URL is expected and matches existing portal route patterns. The URL does not leak across origins because `VITE_MAIN_DOMAIN` is the app's own domain. |
