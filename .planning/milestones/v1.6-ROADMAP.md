# Milestone v1.6: Domain Management v2

**Status:** ✅ SHIPPED 2026-05-31
**Phases:** 22–24
**Total Plans:** 11

## Overview

Full DNS-verified custom domain lifecycle management: automated background verification and health monitoring jobs, domain freeze/unfreeze on Pro plan downgrade/upgrade, owner email notifications, Rack-layer 301 redirect enforcement for non-primary domains, and a polished role-gated Domain UI with a 4-step add wizard, on-demand verify, and primary/delete flows.

## Milestone Summary

**Key Decisions:**

- `verify` action uses synchronous `dns_resolves?` inline — frontend expects direct `{ verified }` response; mirrors onboarding verify pattern
- `DomainRedirectMiddleware` uses `insert_before ActionDispatch::Static` — places after Rack::Cors so CORS OPTIONS requests are handled before redirect logic
- In-memory `.find` on `.includes()` collection for primary lookup — avoids second AR query per redirected request
- `unfreeze_custom_domains!` uses `verified` flag to determine restore target — `verified:true → active`, `verified:false → pending`; no pre-freeze status tracking needed
- `alias_method :create, :update` in `Ops::PlanController` — enables POST alongside PATCH/PUT without duplicate action code
- DNS stub via `define_method`/`remove_method` (Minitest 6) — cleanest compatible stub; no module prepend teardown complexity
- `FakeJob` subclass for DNS testing — Minitest 6.0.3 (Ruby 4.0.0) removed `Minitest::Mock` and `.stub`; test subclass overrides `cname_resolves_to_subdomain?` directly
- `useVerifyDomain` uses `onMutate` snapshot for rescue detection — captures previousStatus before mutation fires; avoids relying on response data alone
- `DomainCard` drives verify spinner from `actions.verifyingDomainId` — Component → Context → Hook pattern; card holds no network state

**Issues Resolved:**

- DVER-05 first-to-verify race condition: pessimistic lock in `DomainVerificationJob` prevents concurrent verification promotions
- Minitest 6 stub compatibility: `FakeJob` subclass pattern works across all Phase 22/24 DNS test scenarios

**Issues Deferred:**

- Multi-domain round-robin / load balancing — not needed at current scale; separate milestone
- Server-side 301 at Caddy/proxy layer — current Rack middleware approach is sufficient; proxy-layer move is a separate infrastructure milestone
- Deeper conflict resolution for simultaneous domain claims — first-to-verify is sufficient for current scale

**Technical Debt Incurred:**

- 1 pending architecture todo: `arch-brokerage-listing-access.md` — rethink listing access model (BrokerageEstate vs board credential JOIN); carry to v1.7
