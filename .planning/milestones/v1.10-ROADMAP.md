# Milestone v1.10: Agent Admin Permissions

**Status:** ✅ SHIPPED 2026-07-10
**Phases:** 30–32
**Total Plans:** 9

## Overview

Extended the `agent` role from group-scoped work into full brokerage-wide admin visibility. Backend RBAC gained a third authorization tier (`require_agent_or_above!`) so agents pass read/group-scoped admin endpoints while every other write endpoint continues to 403 them, backed by an exhaustive allow/deny permission-matrix test suite (Phase 30). The admin dashboard shell itself opened to agents on both subdomain and main-domain surfaces, unlocking full CRUD on groups, filter sets, group members/invitations, and group listings (Phase 31). Visibility then widened from "groups only" to all six admin sections — Users, Brokerage, Boards, Domains, Settings — at a strict read tier: every mutation control (edit/delete/invite/domain actions) gated behind `manage_users`/`manage_brokerage_settings`, with brokerage-level staff invitations fully blocked at both the route and UI layer (Phase 32). A UAT round caught a two-layer gap — a JSX-only permission gate couldn't stop an ancestor hook's data fetch, so agents still triggered a (correctly-403'd but user-visible) invitations request on `/admin/users` — closed by a follow-up gap-closure plan that gated the fetch itself via the same `usePermission` primitive.

## Phases

### Phase 30: Backend RBAC Enforcement

**Goal**: The backend correctly enforces `agent` permissions everywhere before any frontend surface is unlocked — group-scoped endpoints accept `agent`, read-only admin endpoints accept `agent`, and every other write endpoint continues to reject `agent` with HTTP 403.
**Depends on**: Nothing (first phase of milestone)
**Requirements**: RBAC-01, RBAC-02, RBAC-03
**Plans**: 2 plans

Plans:
- [x] 30-01: Add `require_agent_or_above!` tier across 5 admin controllers; flip D-03 assertion (wave 1)
- [x] 30-02: Full agent permission matrix — allow-list 2xx + deny-list 403 test coverage (wave 2)

**Details:**
Added a third `require_agent_or_above!` authorization tier (owner/admin/agent) as the default `before_action` on `V1::Admin::BaseController`, propagating agent read/group access to all 13 admin controllers, while stacking narrower `require_admin!`/`require_owner!` checks on the 4 controllers whose write actions must stay blocked for agent. Extended `admin_authorization_test.rb` into an exhaustive agent permission matrix — 46 allow-list assertions (2xx) covering every group-scoped and read-only admin endpoint, 16 deny-list assertions (403 + `error.code == "forbidden"`) covering every write endpoint outside Groups scope, including all four brokerage-level invitation endpoints at their correct collection-vs-member route forms.

### Phase 31: Agent Dashboard Access & Group Management

**Goal**: An `agent` can open the admin dashboard and fully manage groups end-to-end — the primary workspace agents need day to day.
**Depends on**: Phase 30
**Requirements**: ACCESS-01, GROUP-01, GROUP-02, GROUP-03, GROUP-04, GROUP-05
**Plans**: 3 plans

Plans:
- [x] 31-01: Backend — agent main-domain portal access, `admin_brokerages_controller.rb` role filter (D-01) (wave 1)
- [x] 31-02: Frontend — agent permission map + subdomain admin shell gate (D-02, D-04, D-05) (wave 1)
- [x] 31-03: Frontend — Groups-only admin nav narrowing for agent, both `SideNav.tsx` and `PortalAdminSideNav.tsx` (D-03) (wave 2)

**Details:**
Widened `V1::Account::AdminBrokeragesController#index`'s role filter to include `agent`, unblocking main-domain `/dashboard` access for agents. Widened `RequireRole` on `AppShellAdmin.tsx` to admit `agent` and set `ROLE_PERMISSIONS.agent = ['access_admin_panel', 'manage_groups']` — zero new UI, the existing group CRUD flow (`/admin/groups/**`) became usable by agent the instant these two gates opened. Narrowed both admin nav surfaces to show only "Listing Groups"/"Groups" for agent role via a new `isGroupsOnlyAdmin` derived flag (subdomain) and net-new `useRole`-based item filtering (main-domain, which had zero gating before this plan).

### Phase 32: Agent Read-Only Access & Access Gating

**Goal**: An `agent` has correctly scoped read-only visibility into brokerage-wide admin surfaces, is fully blocked from brokerage-level staff invitations, and never sees a mutation control that would 403.
**Depends on**: Phase 30, Phase 31
**Requirements**: ACCESS-02, ACCESS-03, ACCESS-04, ACCESS-05, ACCESS-06, ACCESS-07, ACCESS-08
**Plans**: 4 plans

Plans:
- [x] 32-01: Route access tiers (`readTierRoles`/`ownerAdminOnly`) + ACCESS-08 `DomainCard` mutation-button fix (wave 1)
- [x] 32-02: Nav expansion to all 6 Admin sections for agent + `isGroupsOnlyRole`/`isGroupsOnlyAdmin` dead-code removal (wave 1)
- [x] 32-03: Users list, brokerage invitations & member-detail mutation gating (`manage_users`) (wave 1)
- [x] 32-04: Gap closure — gate the brokerage-invitations fetch (`enabled: manage_users`) so agents never issue the 403ing request on `/admin/users` (wave 1, gap closure)

**Details:**
Opened six admin routes to `agent` at the read tier via a new `readTierRoles` `RequireRole` helper, kept the two mutation-only routes owner/admin-locked, and fixed `DomainCard.tsx`'s `access_admin_panel`-gated "Verify now"/"Upgrade plan" buttons to use `manage_brokerage_settings`, matching the card's existing owner-only mutation gates. Removed the Phase-31 Groups-only nav restriction so agent sees the full 6-item Admin nav on both subdomain and main-domain surfaces, then deleted the now-dead `isGroupsOnlyRole`/`isGroupsOnlyAdmin` helpers with zero remaining references. Gated every previously-ungated mutation control on the Users list, brokerage invitations view, and member detail page behind `manage_users`, including a full `<InvitationsView>` render gate that closed an ACCESS-07 "no view" gap the plan's own CONTEXT.md under-specified. Human UAT then caught that the render gate alone couldn't stop the ancestor `useUsersAdminContext` hook's data fetch — agents still triggered `GET /v1/admin/invitations` (correctly 403'd server-side, but visible in devtools). Gap-closure plan 32-04 added an `{ enabled }` option to `useFetchBrokerageInvitations` driven by `usePermission('manage_users')`, mirroring the existing `useFetchActivityFeed` convention, closing the gap at both layers (no render AND no fetch). Re-verified and human-UAT-approved 2026-07-10.

## Milestone Summary

**Key Decisions:**

- Three-tier backend authorization (`require_owner!` / `require_admin!` / `require_agent_or_above!`) layered as narrower checks stacked on top of a widened default, rather than per-action allow-lists — matches the existing `Admin::BaseController` concern pattern
- Reused the existing 4-permission model (`access_admin_panel`, `manage_brokerage_settings`, `manage_users`, `manage_groups`) rather than introducing new granular permissions — the combination with the shell-level role gate already produces the desired read/write split
- Brokerage-level staff invitations blocked entirely (no partial read-only view) rather than split into partial access — no UI exists for read-only invitation viewing outside the creation form itself
- Established pattern: when a permission-gated JSX section is fed by a parent context hook's data fetch, gate the fetch itself via an `{ enabled?: boolean }` options arg driven by `usePermission` — a `<Can>` render gate alone cannot stop an ancestor's hooks from firing (discovered via the 32-03 → 32-04 UAT gap)

**Issues Resolved:**

- ACCESS-07 "no view" gap: agent-visible 403 network error on `/admin/users` from an ungated ancestor hook fetch, closed via 32-04
- Domain-mutation buttons gated on the wrong permission (`access_admin_panel` instead of `manage_brokerage_settings`), fixed in 32-01
- Dead code (`isGroupsOnlyRole`/`isGroupsOnlyAdmin`) removed once nav scope widened past "groups only" in 32-02

**Issues Deferred:**

- None new this milestone — all 16 v1.10 requirements shipped and verified

**Technical Debt Incurred:**

- `useUsersAdminContext.tsx`'s `useMemo` omits `groupsQuery`/`invitationsQuery`/`inviteFilter` from its dependency array (flagged in 32-04-REVIEW.md, WR-01) — currently safe by accident (a sibling hook returns a new object every render), but fragile and directly adjacent to the new gating logic
- Hook test coverage for the invitations gate only covers `agent`/`admin` roles — missing `owner`, `staff`/`client`, and the "role not yet loaded" transient state (the actual fail-closed mechanism)
