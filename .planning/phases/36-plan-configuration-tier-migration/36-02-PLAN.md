<objective>
Migrate `Brokerage#plan` from the binary `basic`/`premium` enum to the three-tier `free`/`independent`/`growth` enum, and rewire every hardcoded plan-string check to the config-driven `plan_config` accessor from plan 36-01.

Purpose: Deliver PLAN-01 (the enum migration with existing rows backfilled and no orphaned/invalid values) and complete PLAN-02 (no plan numbers hardcoded in controllers — all checks now go through the centralized config).

Output: one Rails migration (backfill `basic`→`independent`, `premium`→`growth`, default `basic`→`free`, with an orphan-check guard), the model validation flip, both controller rewires, and the seven test files updated to the new tier literals.

## ATOMIC UNIT — why this is one plan
The model's `validates :plan, inclusion:` flip is a linchpin: the moment it changes to `%w[free independent growth]`, every test that constructs a brokerage with `basic`/`premium` fails, the test factory's column default (`basic`) becomes invalid, and the two controllers' old `== "premium"` checks become semantically wrong for migrated data. These pieces cannot be split across plans without leaving the suite red between them, so they ship together. Task verifies are scoped; the final task runs the full suite green.

## ⚠ ROLLOUT / DEPLOY-SEQUENCING RISK (D-08) — operator must read before deploy
This plan tightens backend validation to `free`/`independent`/`growth` with **NO backward-compatible aliasing** for `basic`/`premium`. The onboarding frontend (`createBrokerageWizard.ts`, `PlanSelectionStep.tsx`) still POSTs only `basic`/`premium` and is not updated until Phase 37. **If this backend deploys before a coordinated frontend fix / before Phase 37 ships, every real onboarding signup will get a 422 "Invalid plan".** The user explicitly accepted this risk (D-08) and will coordinate deploys manually (backend + frontend together, or a short accepted downtime window). Do NOT silently deploy this backend-first. Surface this in the SUMMARY's rollout notes.
</objective>
