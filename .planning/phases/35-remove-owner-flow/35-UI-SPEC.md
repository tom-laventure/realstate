| Destructive | `--destructive` (oklch(0.577 0.245 27.325)) | **Newly activated this phase.** Remove icon-button hover state (`hover:text-destructive hover:bg-destructive/10`, per D-01); Step 3 final "Confirm Role Change" button (`bg-destructive text-destructive-foreground hover:bg-destructive/90`, exact class string borrowed from `DeleteDomainDialog.tsx`'s `AlertDialogAction`) |
| Warning (non-destructive caution) | `amber-50` bg / `amber-300/60` border / `amber-900` text (Tailwind arbitrary, established codebase pattern) | Remove Owner Step 1 warning block; unchanged Add Owner warning callout (now living on its existing step 1, before the new review step) |

Accent reserved for: the radio group's selected-option fill, the non-destructive "advance to next step" buttons (Remove Owner Step 1→2, Step 2→3-is-review-not-primary — see note below, Add Owner step 1's "Continue to Review"), and `StepDots` active/completed dots. ## Component-Level Notes (executor guidance, not in template but load-bearing)

- **Dialog primitive choice:** `RemoveOwnerDialog.tsx` uses plain `Dialog` (not `AlertDialog`) — this codebase reserves `AlertDialog` for single-step, non-interactive destructive confirmations (`DeleteDomainDialog.tsx`); multi-step flows use `Dialog` with internal `useState` step control (`AddDomainWizard.tsx` is the exact precedent, 4 steps → 3 steps here).
- **Step state pattern:** `useState<1 | 2 | 3>(1)` + `goNext`/`goBack` helpers, full reset (`setStep(1)`, clear `selectedRole` back to `'admin'`) inside `handleOpenChange` only when `nextOpen === false` — matches D-05's "no resume mid-flow" requirement exactly. `AddOwnerDialog.tsx`'s retrofit uses the same pattern at `useState<1 | 2>(1)`, resetting `selectedUser` to `null` on close (already implemented) with `step` reset added alongside it.
- **Tooltip-on-disabled-button pitfall (OWN-10):** `buttonVariants` includes `disabled:pointer-events-none`, so a `disabled` native `<button>` never receives hover/focus and a `TooltipTrigger asChild` wrapping it directly will never open. Wrap the disabled `Button` in a focusable `<span tabIndex={0} className="inline-block">` and make that span the `TooltipTrigger`. `TooltipProvider` must wrap the whole `CurrentOwnersList` render (matches `DomainCardList.tsx` convention), not be applied globally.
- **Self-demotion detection data dependency:** `RemoveOwnerDialog` receives `currentUserId` as a prop sourced from `useSettingsAdminContext` (`state.account.id`). The Brain must call `useGetCurrentUser()` unconditionally so `account.id` is populated on both the subdomain and main-domain/portal shell paths (see `35-RESEARCH.md` Pitfall 1) — without this fix, the self-demotion warning sentence and Redux post-demote patch silently never fire on the portal path. This is a functional prerequisite for the copy above to ever render correctly, not purely a visual concern.
- **Radio group accessibility:** `RadioGroup` + `RadioGroupItem` + `Label` (paired via matching `id`/`htmlFor`, e.g. `role-admin`) gets full keyboard arrow-key navigation and `aria-checked` for free from `@radix-ui/react-radio-group` — no custom ARIA work needed.
- **Row layout unchanged:** `CurrentOwnersList.tsx`'s existing row structure (`flex items-center justify-between py-3`, `divide-y divide-border`, no avatars/badges/timestamps, per Phase 34 D-01/D-02) is unchanged — the Remove icon button is appended to the existing row, not a layout rework.
