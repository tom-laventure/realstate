## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client UI → user feedback channel | The dialog state machine is the only surface communicating connect-flow failures to the admin. A silently-swallowed error is a UX integrity boundary issue, not a network boundary issue. No new external trust boundary is crossed by this change. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-13-02-01 | Information Disclosure | serverError rendered into DOM | accept | The serverError value originates from `axiosError?.response?.data?.error` with a hardcoded fallback `'Connection failed. Please try again.'`. Backend `V1::Admin::BoardCredentialsController` returns sanitized human-readable messages (no stack traces, no DB schema leaks). The same rendering pattern is already in production use in the credentials step — this change extends an established, reviewed surface. No new disclosure vector. |
| T-13-02-02 | Repudiation | User claims they never saw an error | mitigate | This plan is the mitigation. Surfacing the error in the DOM gives the admin clear visual confirmation of failure (versus the current state where the Connect button silently re-enables with no message). Combined with the existing toast surface in the parent context for non-422 failures, the failure is now multi-channel observable. |
| T-13-02-03 | Tampering | Stale serverError persisting across step navigation | mitigate | Edit 2 adds `setServerError(null)` to the test-board-info Back button onClick — mirroring the credentials step. This prevents a user who hit an error, navigated Back to select, picked a different board, and re-entered the test-board flow from seeing the previous error message attached to the new context. handleOpenChange already clears serverError on dialog close, so the cross-session vector is already covered. |
</threat_model>
