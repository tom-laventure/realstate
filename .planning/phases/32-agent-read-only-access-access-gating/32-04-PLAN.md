<objective>
Close the sole remaining Phase 32 UAT gap: an agent-role user on `/admin/users` still fires `GET /v1/admin/invitations` and gets a (correct) 403, because the fetch is triggered unconditionally by the ancestor hook chain — `UsersAdminBoard` → `useBrokerageUsersAdminContext` → `useFetchBrokerageInvitations` — long before the `<Can permission="manage_users">` JSX gate (added in 32-03) can hide the rendered section. `<Can>` is a child in the render tree; it cannot stop a parent's hooks from running.

The 32-03 fix correctly hid the Invitations UI, but ACCESS-07 ("agent fully blocked, no view") also requires the frontend to never request the data. This plan gates the fetch itself so the request is never issued for a role that lacks `manage_users`. Backend behavior is unchanged and out of scope (its 403 via `require_admin!` on `InvitationsController#index` is intentional and correct).

Approach follows the codebase's established pattern for conditionally-enabled queries (`useFetchActivityFeed(params, { enabled })`, `useFetchSelectedGroup(params, { enabled })`): add an optional `{ enabled?: boolean }` options arg to the leaf hook and drive it from the same `usePermission('manage_users')` primitive the `<Can>` component already uses — no new convention invented.

Purpose: Eliminates the agent-visible 403 network error on `/admin/users` and fully satisfies ACCESS-07's "no view" requirement (no render AND no fetch).
Output: `useFetchBrokerageInvitations.tsx` gains an `enabled` option; `useUsersAdminContext.tsx` passes the permission gate; a new hook test proves agent→enabled:false, admin→enabled:true.
</objective>
