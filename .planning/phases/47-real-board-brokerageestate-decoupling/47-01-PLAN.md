<objective>
Stop `BoardCredentialsController#create` from bulk-inserting `BrokerageEstate` rows for real (non-test) boards, and switch the brokerage-wide `total_active_listings` admin stat off the `BrokerageEstate` join and onto `Estate.accessible_by`.

Purpose: `Estate.accessible_by`'s first `EXISTS` branch already grants real-board access via the `BrokerageBoardCredential` JOIN, so real-board `BrokerageEstate` rows are pure duplication (ARCH-01). The stat must move first-class onto `accessible_by` or it silently undercounts once those rows stop being written (ARCH-02).
Output: Two controller edits — one conditional guard, one scope swap — with no behavior change for TEST-board connects.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| authenticated admin → `POST /v1/admin/board_credentials` | Admin-supplied `real_estate_board_id` selects which board's estates get access rows |
| authenticated admin/owner → `GET /v1/admin/groups` | Stat response leaks a count of accessible listings; must not count listings outside the tenant's access |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-47-01 | Elevation of Privilege | `BoardCredentialsController#create` — D-02 conditional | mitigate | The guard is `if board.is_test_board?` on a `RealEstateBoard` row loaded server-side by primary key (line 26), never from request params. It cannot be miscomputed by client input: an attacker choosing a real board id gets `false` (no rows, access still granted only by the credential JOIN which requires a *saved, active, non-deleted* credential for their own brokerage); choosing the TEST board id gets `true` (rows inserted exactly as today, which is the pre-existing behavior TEST access already depends on). There is no path where a real board "incorrectly keeps inserting rows" (the guard is a plain boolean read) or where the TEST board "stops granting access" (the guard's true-branch body is unchanged). The plan-gate at line 31 (`plan_config.real_boards || board.is_test_board?`) and the RETS auth at lines 38-46 still run before this code, unchanged. |
| T-47-02 | Information Disclosure | `GroupsController#brokerage_wide_stats` — `Estate.accessible_by` swap | mitigate | `accessible_by` is parameterized on `:brokerage_id` bound from `Current.brokerage.id` (server-derived from the request host via `BrokerageAuth`), never from params — no SQL injection surface and no cross-tenant count. Both `EXISTS` branches filter on that same `brokerage_id`, so the new count is a strict statement of this tenant's access. `.without_deleted` is retained so soft-deleted estates are not counted. |
| T-47-03 | Tampering | Real-board access after ARCH-01 | accept | Removing real-board `BrokerageEstate` rows removes a *redundant* grant, not the only grant: branch 1 of `accessible_by` already covers it, and revoking a credential (soft-delete / status change) now correctly revokes access instead of leaving an orphaned `BrokerageEstate` row behind. This is a net reduction in stale-grant risk. |
| T-47-SC | Tampering | npm/pip/cargo installs | n/a | No package installs in this plan — no `Gemfile`/`package.json` change. Package Legitimacy Gate does not apply. |
</threat_model>
