**`up`** — a single `DELETE FROM brokerage_estates` whose `WHERE` is one correlated `EXISTS` subquery selecting from `estates e` joined to `real_estate_boards reb` on `reb.id = e.real_estate_board_id` and joined to `brokerage_board_credentials bbc` on `bbc.real_estate_board_id = reb.id`, correlated with `e.id = brokerage_estates.estate_id` and `bbc.brokerage_id = brokerage_estates.brokerage_id`, and filtered on:
  - `reb.is_test_board = false`
  - `bbc.status = 'active'`
  - `bbc.deleted_at IS NULL`

This is D-09's predicate expressed as one `EXISTS` rather than two (the second `EXISTS` in CONTEXT.md's `<specifics>` references the alias `e` from the first, which is not valid SQL when written as two sibling subqueries — collapsing them into one correlated `EXISTS` is semantically identical and is the required form). Deliberately do **not** filter on `e.deleted_at` in `up` — that matches D-09's stated predicate.

**`up` guard (post-condition, per D-10 and the plan-tier precedent — guard runs after the delete):** re-run a `SELECT COUNT(*) AS cnt FROM brokerage_estates WHERE <the identical EXISTS predicate>`, read `.first["cnt"].to_i`, and `raise` with a message naming the count and instructing the operator to investigate if it is greater than zero.

**`down`** — an `INSERT INTO brokerage_estates (brokerage_id, estate_id, created_at, updated_at)` fed by a `SELECT bbc.brokerage_id, e.id, NOW(), NOW()` over `brokerage_board_credentials bbc` joined to `real_estate_boards reb` on `reb.id = bbc.real_estate_board_id AND reb.is_test_board = false` and joined to `estates e` on `e.real_estate_board_id = reb.id AND e.deleted_at IS NULL`, filtered `bbc.status = 'active' AND bbc.deleted_at IS NULL`, terminated with `ON CONFLICT (brokerage_id, estate_id) DO NOTHING` so it is idempotent against the existing unique index and never collides with surviving TEST-board rows.

Add file-header comments recording, per D-11: (a) `down` replays BOARD-03's `insert_all` semantics rather than restoring an exact byte-for-byte snapshot — `created_at`/`updated_at` are set to rollback time, which is accepted; (b) `down` restores rows only for non-deleted estates (matching BOARD-03's `without_deleted`), so a row `up` deleted for an already-soft-deleted estate is not recreated — also accepted, since `Estate.accessible_by` and every consumer scope soft-deleted estates out anyway; (c) a cross-reference to `Estate.accessible_by`'s real-board branch as the source of the predicate, and to ARCH-05 / D-09.

Do not use `Estate`, `BrokerageEstate`, or `BrokerageBoardCredential` ActiveRecord classes anywhere in the migration — raw SQL only, so `acts_as_paranoid` default scopes and future model changes cannot alter what this migration does.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| migration runner → production data | a `DELETE` with no `WHERE` mistake or an over-broad predicate silently revokes real access grants |
| shared board data → per-brokerage access rows | `brokerage_estates` is one of the two branches `Estate.accessible_by` reads for access |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-47-08 | Denial of Service (access revocation) | `up`'s DELETE deleting a row that is NOT actually redundant | mitigate | Walk the predicate: a row is deleted only when there exists an `estates` row `e` with `e.id = brokerage_estates.estate_id` **and** a `real_estate_boards` row with `reb.id = e.real_estate_board_id AND reb.is_test_board = false` **and** a `brokerage_board_credentials` row with `bbc.real_estate_board_id = reb.id AND bbc.brokerage_id = brokerage_estates.brokerage_id AND bbc.status = 'active' AND bbc.deleted_at IS NULL`. Those are exactly the conditions of `Estate.accessible_by`'s first `EXISTS` branch, evaluated for the *same* `brokerage_id` that owns the row — so every deleted row's access is still granted by branch 1. Rows are untouched when: the estate has `real_estate_board_id IS NULL` (manual estate — the join to `real_estate_boards` fails), the board is the TEST board (`is_test_board = false` fails, and branch 1 of `accessible_by` excludes test boards, so those rows remain the only grant), or the brokerage's credential is `invalid`/`suspended`/soft-deleted (no active credential ⇒ predicate false ⇒ row preserved). No false positive can revoke real access. |
| T-47-09 | Tampering | Silent partial delete leaving the DB in a half-cleaned state | mitigate | Post-condition guard re-counts rows matching the identical predicate after the DELETE and `raise`s a named, human-actionable error if any remain — the plan-tier migration's proven pattern (D-10). Rails wraps the migration in a transaction, so a raise rolls the DELETE back. |
| T-47-10 | Repudiation | Irreversible data loss (no way back) | mitigate | `down` repopulates via `INSERT ... SELECT` over every active non-test-board credential's non-deleted estates with `ON CONFLICT DO NOTHING` (D-11), and the up→down→up round trip is executed against the test DB in Task 2 as a gate, not left to inspection. The two accepted asymmetries (rollback-time timestamps; soft-deleted estates not restored) are documented in the migration header. |
| T-47-11 | Elevation of Privilege | `down` granting access to a brokerage that should not have it | mitigate | `down` inserts only `(bbc.brokerage_id, e.id)` pairs where that brokerage holds an `active`, non-deleted credential for the board the estate belongs to — a strict subset of what `accessible_by` branch 1 already grants that brokerage. Rolling back therefore cannot widen access beyond the pre-migration state. |
| T-47-12 | Tampering | `acts_as_paranoid` default scopes hiding rows from the migration | mitigate | Raw SQL only — no `Estate`/`BrokerageEstate`/`BrokerageBoardCredential` AR usage (asserted in Task 1's acceptance criteria), so soft-delete default scopes cannot change which rows the migration sees, exactly as the plan-tier migration reasoned. |
| T-47-SC | Tampering | npm/pip/cargo installs | n/a | No package installs in this plan — no `Gemfile` change. Package Legitimacy Gate does not apply. |
</threat_model>
