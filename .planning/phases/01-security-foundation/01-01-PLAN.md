<objective>
Install rack-attack and solid_cache gems, run solid_cache migrations, and configure Rails.cache in all three environment files.

Purpose: rack-attack depends on a shared cache store (solid_cache) for cross-Puma-worker rate limiting counters. Rails environment files must configure `config.cache_store = :solid_cache_store` — NOT in an initializer — because `rack_attack.rb` initializer loads alphabetically before `solid_cache.rb`. If Rails.cache is configured in an initializer, rack_attack.rb copies the wrong (null) store. This is Wave 1: no other plan can depend on Rack::Attack or Rails.cache until this completes.
Output: rack-attack gem available, solid_cache tables in database, Rails.cache = SolidCache in all environments.
</objective>

Placement: add it near the top of the configure block, before any `config.action_dispatch` or middleware config lines. It must be a top-level `config.*` call inside the block, not nested inside a conditional.

Per D-20: no `database.yml` entry needed. solid_cache uses the primary PostgreSQL connection when no `connects_to` is configured and no `config/cache.yml` is present.

Per Pitfall 1 from RESEARCH.md: this setting MUST be in environment files (loaded before all initializers), NOT in `config/initializers/solid_cache.rb`. `rack_attack.rb` comes before `solid_cache.rb` alphabetically — if `Rails.cache` is set in an initializer, `Rack::Attack.cache.store = Rails.cache` in rack_attack.rb would copy the null store. Setting it in environment files ensures `Rails.cache` is already the SolidCache store when any initializer runs.

For `test.rb`: still set `:solid_cache_store` so that test-suite rate limiting uses the same path as production. If the test suite's test helper needs to reset the store between tests, that is a Phase 2 concern.
