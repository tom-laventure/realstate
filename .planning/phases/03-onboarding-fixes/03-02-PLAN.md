Purpose: New invitees must land on a real page after accepting. The router has routes like `/:groupUid` and `/` but no `/dashboard`, no `/dashboard/:integer`, and no `dashboard/:uid` (relative).

Output: Backend returns group.uid; both frontend invitation flows navigate to absolute paths and handle the "dashboard" sentinel correctly.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → /v1/dashboard/invitations/accept | Authenticated user crosses here; invitation token previously validated in token branch |
| Browser → /v1/dashboard/invitations/accept_token | Public — invitation token from URL crosses here unauthenticated then authenticated |
| Backend → Frontend response (next_step) | Server-controlled string; frontend interpolates into a router path |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-02-01 | Tampering | next_step value forwarded to frontend | mitigate | next_step is server-derived from `group.uid` (UUID column on the Group model) or the literal string `"dashboard"` — never user-supplied; the frontend's react-router treats unknown paths as 404 not-found, not as a privilege boundary |
| T-03-02-02 | Information Disclosure | next_step exposing group.uid | accept | UID is intentionally a non-sequential identifier designed to be exposed in URLs (this is its primary use) — no enumeration vector created |
| T-03-02-03 | Elevation of Privilege | accept_token branch with brokerage-level invitation | mitigate | Pre-existing Phase 1 (D-14) test confirms accept_token validates the invitation token and links the user to the inviting brokerage's membership; this plan does not alter the membership-creation logic — only the response field |
| T-03-02-04 | Spoofing | client navigation to `/${nextStep}` | accept | nextStep is controlled by the server in the same response; even if MITM tampered with the value, the worst case is a router 404 — no auth bypass since auth state is in cookies/local storage, not the path |
| T-03-02-05 | Repudiation | post-invite landing-page change | accept | Existing audit trail from invitation accept is unchanged — the invitation record is still updated with accepted_at server-side; only the UI redirect target differs |
</threat_model>
