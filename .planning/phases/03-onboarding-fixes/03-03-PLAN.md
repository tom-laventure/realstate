# POST /v1/account/profile/dismiss_welcome
def dismiss_welcome
  membership = BrokerageMembership.without_deleted.find_by!(

end

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → POST /v1/account/profile/dismiss_welcome | Authenticated user; no params; uses Current.user + Current.brokerage |
| BrokerageMembership row → response | Server reads welcomed_at; exposes derived show_welcome_banner boolean (not the timestamp) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-03-01 | Spoofing | dismiss_welcome called by another user | mitigate | `BrokerageMembership.without_deleted.find_by!(user_id: Current.user.id, brokerage_id: Current.brokerage.id)` constrains lookup to the authenticated user's own non-deleted membership in the resolved brokerage; cross-user dismissal is impossible |
| T-03-03-02 | Tampering | client manipulating welcomed_at value | mitigate | Action accepts no params; the server hardcodes `welcomed_at: Time.current` — no client-supplied value is honored |
| T-03-03-03 | Information Disclosure | UserSerializer leaking welcomed_at timestamp | accept | Only the derived boolean `show_welcome_banner` is exposed (D-16); the raw timestamp is not added to the payload — minimal information leakage |
| T-03-03-04 | Denial of Service | repeated dismiss calls | accept | Each call is a single update on one row; existing Phase 1 rate limits on /v1/* protect general abuse; idempotent semantics (welcomed_at simply re-set to a newer Time.current) cause no consistency issue |
| T-03-03-05 | Elevation of Privilege | endpoint exposed without auth | mitigate | ProfileController already includes `CognitoAuth` + `BrokerageAuth` + `before_action :authenticate_cognito_user!` — new action inherits the stack; no new authorization surface to verify |
| T-03-03-06 | Information Disclosure (cross-tenant) | Current.brokerage misalignment | mitigate | BrokerageAuth concern resolves Current.brokerage from request host BEFORE controller action runs (Phase 1); membership lookup uses Current.brokerage.id — cross-tenant write is impossible by construction |
| T-03-03-07 | Spoofing | soft-deleted membership re-activated by dismiss | mitigate | `.without_deleted` scope EXCLUDES soft-deleted memberships from the lookup — a removed user cannot dismiss a banner on a brokerage they were removed from; instead, the action 404s |
</threat_model>
