<objective>
Restructure `Estate#accessible_by` so estates on a TEST board become visible to a brokerage once a `BrokerageEstate` row exists, without losing the existing real-board access semantics.

Purpose: After Plan 02 creates `BrokerageEstate` rows for TEST-board listings, the dashboard / group / filter-set queries still cannot see those listings because the current `accessible_by` scope hard-filters to `real_boards` via `joins(:real_estate_board).merge(RealEstateBoard.real_boards)`. That outer JOIN drops every TEST-board estate before the EXISTS checks can run. The fix moves the `real_boards` constraint INSIDE the first EXISTS (real-board credential path) and leaves the second EXISTS (BrokerageEstate path) board-type-agnostic. The result: BOARD-03's BrokerageEstate inserts become visible everywhere `accessible_by` is used (5 callers across estates_controller, group/estates_controller, filter_set_estates_query, group_estates_query, services/groups/create, sync_listing_photos_job).

Output:
- Rewritten `accessible_by` scope in `estate.rb`.
- New scope unit-test file covering 7+ behavioral cases.

<sql_diff_explanation>
**Why the outer `joins+merge` must be removed:**

Current SQL (simplified):
```sql
SELECT estates.* FROM estates
INNER JOIN real_estate_boards ON real_estate_boards.id = estates.real_estate_board_id
WHERE real_estate_boards.is_test_board = false
  AND (EXISTS (... bbc) OR EXISTS (... be))
```
The `INNER JOIN ... WHERE is_test_board = false` runs BEFORE the OR — TEST-board estates never enter the candidate set. Even if `EXISTS (... be)` would match, the row is already discarded.

After (target) SQL (simplified):
```sql
SELECT estates.* FROM estates
WHERE EXISTS (
        SELECT 1 FROM real_estate_boards reb
        JOIN brokerage_board_credentials bbc
          ON bbc.real_estate_board_id = reb.id
         AND bbc.brokerage_id = $1
         AND bbc.status = 'active'
         AND bbc.deleted_at IS NULL
        WHERE reb.id = estates.real_estate_board_id
          AND reb.is_test_board = false
      )
   OR EXISTS (
        SELECT 1 FROM brokerage_estates be
        WHERE be.brokerage_id = $1
          AND be.estate_id = estates.id
      )
```
- Real-board protection preserved: first EXISTS still requires `reb.is_test_board = false`.
- Test-board access path: second EXISTS does not touch `real_estate_boards`; if a `brokerage_estates` row exists for (brokerage, estate), the estate is returned — regardless of board type.
- Real boards remain protected: a real-board estate with NO `bbc` row AND NO `be` row is not returned. (Same as before.)
- Nil board_id estates: `estates.real_estate_board_id` IS NULL → first EXISTS `WHERE reb.id = NULL` matches nothing → only the second EXISTS can return them (correct).
</sql_diff_explanation>
