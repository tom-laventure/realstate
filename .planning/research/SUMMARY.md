# Research Summary: RealState SaaS — Milestone 2

**Domain:** Multi-tenant real estate SaaS — security hardening, social auth, calendar sync, onboarding fixes, test suite
**Researched:** 2026-04-30
**Overall confidence:** HIGH

---

## Executive Summary

This milestone adds five distinct capability areas to an already-running Rails 7.1 / React 18 platform: server-side RBAC enforcement, Google social login via Cognito, personal calendar sync (Google/Apple/Microsoft), onboarding bug fixes, and a new test suite. The existing stack handles all of this without new frameworks — only targeted library additions are needed. Every piece is additive to existing architecture.

The single most important finding is a structural blocker for Google OAuth: Cognito's `redirectSignIn` allowlist requires exact-match URLs. Because the app serves each brokerage on a unique subdomain, every new brokerage domain would require a Cognito configuration update — or the login would fail with a redirect mismatch. This must be resolved in design before any OAuth code is written. The recommended solution is a single fixed intermediary callback URL (e.g. `auth.yourdomain.com/oauth/callback`) that receives all OAuth redirects, extracts brokerage context from the `state` parameter, and then redirects to the correct subdomain to complete the session exchange.

Apple CalDAV is a second architectural surprise: Apple does not support OAuth2 for iCloud calendar access. The only available mechanism is an app-specific password generated by the user at appleid.apple.com. This means the Apple calendar connection UI must present a credential form rather than an OAuth consent screen, credentials must be stored encrypted (ActiveRecord Encryption is already configured), and the Apple provider implementation is a distinct workstream from Google and Microsoft.

## Key Findings

### From STACK.md

**Google OAuth:** No new packages needed. `aws-amplify` 6.15.9 already ships `signInWithRedirect` and Hub. The backend flow is unchanged — Cognito issues its own JWT after the Google handshake; `CognitoAuth` + `TokenService` process it identically to password login. Account linking uses `AdminLinkProviderForUser` via the already-installed `aws-sdk-cognitoidentityprovider` gem, triggered from a Cognito Pre Sign-Up Lambda.

**Calendar sync gems:**
- Google Calendar: `google-apis-calendar_v3` (~> 0.29) + `googleauth` (~> 1.11) — official Google libraries; custom `TokenStore` persists tokens to `UserCalendarConnection` in PostgreSQL
- Microsoft Calendar: `oauth2` (~> 2.0) + existing `httparty` — `msgraph-sdk-ruby` was archived July 2025, never use it
- Apple Calendar: `calendav` (~> 1.0) + app-specific password — Apple has no OAuth2 for CalDAV; credential stored with `encrypts` (already configured)

**Testing stack:**
- Backend: add `factory_bot_rails` + `shoulda-matchers` to existing Minitest setup; use `ActionDispatch::IntegrationTest` with real `TokenService`-issued JWTs and `Host` header for tenant resolution
- Frontend: add `vitest` + `jsdom` + `msw` (v2); Vitest reuses existing `vite.config.ts` with a `test:` block; MSW intercepts network layer (TanStack Query maintainer's recommended approach over mocking axios directly)

### From FEATURES.md

**Must-haves (table stakes):**
- Google "Continue with Google" button at equal weight to email/password
- Automatic account linking by email (via PreSignUp Lambda — not default Cognito behavior)
- Calendar management panel: connect, disconnect, sync status per provider
- `EstateDate` sync on create/update/delete to all connected calendars
- Sync failure indicator + `last_error` surfaced in settings panel
- Server-side 403 on admin endpoints (currently frontend-only guard — active security gap)
- Domain setup step completion without crash
- Post-join redirect to brokerage workspace (not homepage)

**Defer (explicitly not this milestone):**
- Two-way calendar sync (requires webhooks, conflict resolution — entirely different scope)
- Apple/Microsoft social login (only Google OAuth for this milestone)
- Audit log of 403 rejections (future security milestone)

**Anti-patterns to avoid:**
- Blocking HTTP requests on calendar API writes — always use SolidQueue jobs
- Syncing all group listing dates to all members' calendars by default — respect opt-in
- Returning 404 instead of 403 for unauthorized admin resources — wrong HTTP semantics
- `msgraph-sdk-ruby` — archived, unmaintained

### From ARCHITECTURE.md

**Cognito Google OAuth flow:** Cognito handles the Google OAuth2 handshake at `/oauth2/idpresponse`. After the redirect, Amplify fires `signInWithRedirect` Hub event → `fetchAuthSession()` → idToken → `POST /v1/sessions` → `TokenService.issue(user)` → HS256 JWT. The entire backend auth path is unchanged. Account linking via Pre Sign-Up Lambda preserves the original Cognito `sub` so `CognitoAuth`'s `find_by(cognito_sub:)` lookup continues to work.

**Calendar token storage:** New `user_calendar_connections` table — one row per user per provider (`google`, `microsoft`, `apple`). Fields: `jsonb :token_data` (access/refresh tokens for Google/Microsoft), `encrypted_credential` (Apple app-specific password via `encrypts`), `string :status` (`connected`/`error`/`disconnected`), `datetime :last_synced_at`, `text :last_error`. Unique index on `[user_id, provider]`.

**Calendar sync job pattern:** `CalendarSyncJob` enqueued after `EstateDate` commits. Idempotency via deterministic provider event ID stored back on `EstateDate` (or a join table). Failure marks the connection `status: 'error'` and continues other providers — never fails the whole job on a single provider error. Retry with `polynomially_longer` — consistent with existing jobs.

**Admin::BaseController:** `V1::Admin::BaseController < ApplicationController` with a single `before_action :require_admin!`. All admin controllers inherit from it. `require_admin!` reads `Current.membership.role` and renders 403 `{ error: { code: "forbidden" } }` for non-`owner`/`admin` roles. The Axios interceptor must add a 403 case (redirect to dashboard + toast) alongside the existing 401 logout handler.

**Minitest multi-tenant pattern:** Use `ActionDispatch::IntegrationTest` (full middleware stack including `BrokerageAuth`). Per-test `Host` header drives tenant resolution. `TokenService.issue(user)` in an `AuthHelper` module mints real JWTs. Two factory-created brokerages per tenant isolation test. Transactional fixtures handle rollback — no DatabaseCleaner needed.

### From PITFALLS.md

**Critical (design decisions required before coding):**

1. **Cognito multi-tenant callback URL conflict** — Cognito requires exact-match `redirectSignIn` URLs. The app serves each brokerage on a unique subdomain, so `window.location.origin` is different for every tenant. A fixed intermediary callback URL with brokerage context encoded in the OAuth `state` parameter is the required solution. This is a design decision that blocks Google OAuth implementation; resolve it before writing any OAuth code.

2. **Account duplication on Google sign-in** — Cognito creates a separate user record for Google sign-in even when the email matches an existing native user. The PreSignUp Lambda calling `AdminLinkProviderForUser` must also verify `email_verified: true` on the Google claim or it enables account takeover. The Lambda also throws an exception on first successful link (known Cognito behavior) — the frontend must catch and suppress it, then retry login.

3. **`email_verified` silently reset on every Google sign-in** — Without explicit attribute mapping in Cognito, `email_verified` resets to `false` on each Google sign-in, breaking email-based password reset for affected users. Map the Google `email_verified` claim to the Cognito attribute explicitly.

**Moderate pitfalls:**

4. **Token refresh race condition in SolidQueue** — Two concurrent calendar sync jobs for the same user both calling the token refresh endpoint will invalidate each other. Use PostgreSQL advisory locks (`UserCalendarConnection.with_advisory_lock(id)`) — no Redis needed since SolidQueue is DB-backed.

5. **Calendar sync duplicate events on retry** — SolidQueue retries failed jobs. Without idempotency, retries create duplicate calendar events. Solution: store the provider-returned event ID on `EstateDate` at write time; check for existence before creating.

6. **DST time drift** — Store timezone as IANA timezone ID (e.g. `America/Vancouver`) on `EstateDate`, never as a UTC offset. Calendar API events created with UTC offsets rather than timezone IDs drift by ±1 hour around DST transitions.

7. **Rack::Attack in-memory store** — Each Puma worker maintains separate rate-limit counters. With multiple workers, rate limits are effectively multiplied by worker count. Requires a shared cache store. PostgreSQL-backed store via `rack-attack` DB adapter is the right call given the existing stack (no Redis).

8. **`Current.brokerage` leaking between Minitest tests** — `CurrentAttributes` resets at `ActionDispatch::Executor` boundaries (request lifecycle), which don't exist in unit tests. Add `teardown { Current.reset }` to `ActiveSupport::TestCase` in `test_helper.rb` on day one of testing setup.

## Implications for Roadmap

Based on combined research, the recommended phase structure is **5 coarse phases** (matching the selected coarse granularity):

### Phase 1: Security Foundation
**Rationale:** Closes an active RBAC security gap and removes hardcoded credentials before adding new entry points (Google OAuth would be a new unauthenticated entry point that lands on an insecure system).
**Delivers:** `Admin::BaseController` with `require_admin!`, 403 handling in Axios interceptor, removed hardcoded credentials, CORS tightened, rate limiting on login endpoint, SQL injection dead code removed, InvitationsController crash fixed, `GroupEstate` cleanup scoped, `per_page` cap enforced, `EstateLike` N+1 fixed, `console.log` cleanup
**Avoids pitfall:** Admin RBAC must be server-side, not frontend-only; 403 must not log out users

### Phase 2: Test Suite Foundation
**Rationale:** Install the safety net before writing any new features. Phase 1 changes (RBAC, auth) are exactly the highest-risk paths that need tests first. Tests for Phase 1 prove it works correctly.
**Delivers:** `factory_bot_rails` + `shoulda-matchers` + `AuthHelper` + tenant isolation tests + admin authorization tests + `Current.reset` teardown; Vitest + MSW + `renderWithProviders` helper + `RequireRole` / `ProtectedRoute` tests
**Research flag:** Standard patterns — no phase-specific research needed

### Phase 3: Onboarding Fixes
**Rationale:** Short focused phase. InvitationsController crash (fixed in Phase 1) was the root cause of the post-join breakage. Domain setup and post-join redirect are the remaining broken pieces. Unblocks new user activation before Google OAuth lands.
**Delivers:** Domain setup validation (format + availability check), domain preview in wizard UI, post-join redirect to brokerage workspace, welcome banner on first dashboard visit
**Avoids pitfall:** Fix in-place (no wizard rewrite); block wizard progression on unsaved state

### Phase 4: Google OAuth
**Rationale:** Cognito configuration, PreSignUp Lambda, and frontend button must ship as a single atomic change — never the button without the Lambda (creates duplicate accounts).
**Delivers:** Cognito Google IdP configuration, intermediary callback URL strategy, PreSignUp Lambda for account linking (`email_verified: true` guard), `signInWithRedirect` button on login screen, Hub listener + session exchange, "Connected via Google" indicator in account settings
**Research flag:** Fixed intermediary callback URL design (multi-tenant subdomain conflict) must be resolved in planning before implementation. PreSignUp Lambda is Node.js (separate Lambda deployment).

### Phase 5: Calendar Sync
**Rationale:** Infrastructure (model + job skeleton) first, then Google (cleanest OAuth, highest value), then Microsoft, then Apple (separate credential form). Deliver incremental value — Google calendar alone is shippable.
**Delivers:** `UserCalendarConnection` model + migration (with `encrypts :credential` for Apple), `CalendarSyncJob` with deterministic event ID idempotency + retry pattern, calendar management panel in user settings, Google Calendar sync (create/update/delete on `EstateDate`), Microsoft Graph sync, Apple CalDAV sync (credential form, not OAuth), sync failure indicator + manual re-sync button, calendar integration tests (WebMock-stubbed)
**Avoids pitfalls:** PostgreSQL advisory lock for token refresh race condition; IANA timezone IDs; Google/Microsoft first (Apple is a distinct auth model)

## Gaps to Address at Planning Time

1. **Fixed intermediary callback URL strategy** — The exact implementation (which URL, how `state` encodes brokerage subdomain, how the intermediary reads it and fires the brokerage redirect) must be designed before Phase 4 planning begins.
2. **Provider event ID storage model** — Two options: columns directly on `EstateDate` (`google_event_id`, `microsoft_event_id`, `apple_event_uid`) vs. a separate `EstateCalendarSync` join table. Decision affects Phase 5 migration design.
3. **`EstateDate` timezone column** — Does it already exist? If only UTC timestamps are stored, a migration adding `timezone: string` is needed before calendar sync ships.
4. **Puma worker count in production** — Determines urgency of Rack::Attack shared store fix. If worker count is 1, the risk is lower (but still present during restart windows).
5. **Apple CalDAV scope** — Personal iCloud only, or does the brokerage use Apple Business Manager? The credential flow differs.
